# Traveler — current product specification

This document combines the [original mission](MISSION_ORIGINAL.md) with the owner's decisions through 2026-11-02. It supersedes contradictory examples in the original. The application is for personally organized trips, starting with one ski trip of approximately 160 participants. Design trip ownership and membership for multiple trips; do not implement speculative travel products. Reassess provider plans if use becomes professional.

The group-transport and interactive-room-planning sections record the current V1 direction. Inline open points must be resolved before implementing those workflows.

## Scope and roles

Identity is global; membership and role belong to a trip. A person can participate in several trips with different roles. Options, rooms, assignments, tickets and requests belong to one trip and cannot refer to another trip's members or resources.

| Role                         | Rights within that trip                                                                                                                                                                                                     |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `traveler` — voyageur        | View own trip information, group itinerary, tickets, activity and assigned room/roommates; declare car/carpool intent when not assigned to a group transport; submit room-change requests and consents. |
| `companion` — accompagnateur | Retain traveler view; process traveler requests; configure group transports and participant assignments; edit participant activity, manage rooming directly, view emergency contacts, and upload transport tickets within the trip. |
| `manager` — gestionnaire     | Retain companion capabilities; edit the trip name, import participants, correct participant email addresses, assign trip roles, and view each member's sign-in history. Managers can generate and copy a single-use login link for support/debugging; generating it does not send an email. |

No public signup. Imported participants receive access using a passwordless email link and a secure persistent session. Importing an email does not establish email verification. Sign-in emails use the sender identity `BotMail <no-reply@joffraybillon.fr>`; verify the sender/domain in Brevo before the first live send. Define initial manager provisioning and recovery before implementing authentication. Participants do not directly edit activity, transport mode, tickets or room assignment. Later, ski day 3 and ski/spa formula changes can be requested and require administrative approval; these forms are outside the initial foundation.

## Rooms and requests

Room inventory is configured per trip by room capacity and quantity. The 2027 ski trip starts with 18 rooms of three and 29 rooms of four: 47 rooms and 170 places for an expected 160 participants. The application assigns each room an anonymous number scoped to the trip; this number is unrelated to the hotel's room number and must not reveal it. Never expose hotel room numbers in traveler-facing views. Preserve any agency workbook's own room identifiers as required for the agency workflow; they are not the application's room numbers.

Organizers can generate an initial room plan and directly move people between rooms with drag and drop. These organizer edits apply immediately and do not create traveler consent requests, including when an organizer's action makes a room mixed. The organizer view is an overview of the complete room plan and its capacities/composition. A traveler can also propose a move with drag and drop; that action creates a request and does not change the assignment until its required approvals are complete. Every traveler whose assigned place changes must approve. If a request results in a mixed room, every person in each resulting mixed room must approve, as previously agreed. A request involving an already mixed room is a room-level request; its exact approvers remain to be confirmed below.

Travelers and organizers can lock a full room to refuse traveler-initiated room-change requests. Organizers retain direct room-management authority. The lock is a request gate, not a hotel lock or a security boundary. Capacity, membership and request rules must still be enforced server-side and applied atomically.

The room-plan generator must never exceed room capacity. It should use the trip's confirmed traveler data and produce a reviewable plan; how it handles gender composition and people it cannot place without creating a mixed room remains to be decided. Actual hotel room numbers remain private and are not imported into this system.

Use a proposed change and a versioned composition to prevent approvals from applying to a different proposal. Consent is scoped to one request and never grants blanket consent to future roommates. Still to decide: whether an existing mixed-room request requires consent from all occupants of that room or only the people whose place changes; who may lock/unlock a full room; the composition constraints and unmatched-person handling for automatic generation; whether a traveler can withdraw a pending request; what happens when a request expires or an already-applied change must be undone; and which notifications are sent. Room locking prevents traveler requests, not direct organizer edits.

## Activities and group transport

Ski and spa profiles are mutually exclusive. Ski day 3 requires the skier profile.

Transport is organized into trip-scoped groups, such as `Paris ski`. An organizer configures each group and assigns travelers to it. A traveler assigned to a group inherits the group's shared itinerary; there are no separate meeting/departure schedules per traveler. The outbound and return journeys may use different modes and each may contain multiple ordered transport segments. The trip currently uses train and flight segments. Configure meeting place/time, departure place/time and other itinerary details at group/segment level; show the same itinerary to every assigned traveler. Tickets and seat assignments can remain traveler-specific.

Travelers marked as having no group transport can declare whether they arrive by car, are willing to drive/carpool, or need a passenger seat. This information supports an organizer's vehicle estimate. Whether the app only counts these declarations or also coordinates driver/passenger matching, and whether drivers enter available seat counts, remains to be decided. Do not model those declarations as personal train/flight schedules.

Organizers configure groups and assignments; travelers do not select or edit their assigned group. Staff may upload tickets and traveler-specific seat information after the group itinerary is configured. Missing details must be displayed clearly. Transport groups and segments must be trip-scoped and have stable identifiers so reassignment does not duplicate traveler data. How source-workbook departure cities map to configured transport groups remains to be decided; imports must not silently invent groups or make ambiguous assignments.

## Import/export and privacy

Participant import uses source-specific `.xlsx` readers rather than the former generated-template-only importer. The detailed order workbook is imported infrequently to enrich product options; the validated-roster workbook is a frequent, complete snapshot joined by normalized `Référence`. Derive payment status from the frequent roster: remaining due of zero means paid, positive remaining due with a positive amount paid means partially paid, and positive remaining due with zero paid means unpaid. Keep payment state and amounts per booking reference and show them only to managers. Show a row-level diff and validation report before writing; detect duplicate/unmatched references and apply each accepted batch atomically. Re-import is idempotent and preserves accounts, history, trip roles, assigned rooms, staff-entered travel details, uploaded tickets, requests and traveler-entered profile data. Missing references cancel those registrations; release the room assignment only if no other active registration remains, and never physically delete the associated account or history. Managers can change participant email addresses with collision checks. Keep booking identity (`Référence`) separate from login identity (email). The companions/VIP workbook is a separate one-time import: `Accompagnant` maps to companion, `Partner` to VIP traveler, and managers are assigned explicitly. For the agency rooming workbook, fill the supplied template without changing its layout; on return, preview exact name matches and block ambiguous or unknown matches. Import only returned train seats. 160 is the expected ski attendance, not a hardcoded system-wide maximum. Limit import and ticket uploads to 4 MB, import to 500 participant rows and 20 MB uncompressed workbook contents; validate activity, transport, times and room references.

On first login, travelers complete or confirm their trip profile: sex (`M`/`F`), dietary requirements, allergens, and emergency contact first name, last name and phone. When source data provides sex, prefill it and require traveler confirmation; otherwise require the traveler to enter it. Explain in a short tooltip that this field is used for rooming controls. Travelers may edit these profile fields but not their email. Emergency contacts are visible to companions for participants in their trip list and to managers through their companion capabilities. Do not include emergency contacts in the agency rooming export unless separately agreed.

The manager supplies the agency's original rooming template when exporting. Fill its existing fields with room occupants, category, activity, transport, dietary requirements, allergens and phone; preserve the layout and train placement columns, and add the third ski day to `Commentaires` without discarding comments. The return import changes only train placement fields and uses a preview. Keep real exports/imports outside the public repository.

Keep tickets in one private Vercel Blob store with authorized server upload/download routes. Prefix paths by Vercel environment and, for previews, deployment branch; keep the path stable across redeployments so a new deployment can still read previously uploaded tickets. Vercel Functions use short-lived OIDC credentials from the connected store; local development outside Vercel uses `BLOB_READ_WRITE_TOKEN` and a `local/` path prefix. Do not log ticket contents, URLs, names or credentials. Retention and backup policy still need to be agreed. Accessibility includes React Aria controls, keyboard/touch alternatives to room drag-and-drop and real mobile verification; see the [guide](contributing/04-accessibility-rgaa.md).

## Current delivery boundary

The current implementation includes tooling, local scripts, an accessible themed shell, API liveness and readiness endpoints, CI/CD configuration and contributor/AI documentation. Existing organizer tools support participant imports, room creation/placement and ticket handling. The group-transport model, configurable anonymous room inventory, complete drag-and-drop room planner and revised room-lock/request rules described above are the target behavior and are not yet fully implemented. Imports, travel details, tickets and room requests remain trip-scoped and server-authorized. Ticket files are stored in private Vercel Blob and streamed only after a membership check. Application startup never applies migrations. GitHub Actions applies pending migrations to production or the `dev` Preview branch using the matching Vercel environment variables before asking Vercel to build and publish the tested commit. Feature previews do not run migrations.

The web interface supports French and English. French is the default; a traveler can select English from the language control, and the selection is kept in that browser.

Live use requires separate environment variables, a migrated database, a provisioned manager, a verified Brevo sender/domain, and the private Blob store connected to the Vercel project. Review the remaining rooming consent lifecycle and ticket retention policy before the first live participant import.
