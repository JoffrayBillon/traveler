# Tests and delivery

Use Vitest for behavior tests, Testing Library and user-event for UI interactions, and axe-core for semantic checks. Test meaningful states, failures and authorization boundaries when introduced. Prefer user-visible outcomes to implementation details. The shell tests cover the skip link, keyboard theme toggle, semantic accessibility and API status/error contracts. jsdom cannot verify visual contrast or actual screen-reader output.

Run the smallest relevant command while editing, then `pnpm check` before integration. Type checks include the Vercel function entry point using its isolated configuration. API tests include a native Node import of the compiled package from the web workspace and actual health/error responses. The Vite build alone does not bundle Vercel serverless functions; remote preview verification is required before claiming deployment success. A Vercel READY state is not evidence that function invocation succeeds.

GitHub Actions CI runs on pull requests and pushes, with read-only repository permission and no service secrets. The deploy workflow is manual and restricted to `main`; it repeats checks before accessing deployment credentials. Its preview and staged-production paths use separate GitHub environments. Configure required reviewers and branch restrictions where available before adding secrets. No workflow promotes a deployment automatically.

Before enabling CD, create/link the Vercel project with root directory `apps/web`, include sources outside that directory, select Node 24, and configure the install/build/output settings in `apps/web/vercel.json`. Configure protected GitHub environments and set `VERCEL_TOKEN` as an environment secret, with `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID` as variables. The workflow pins the reviewed Vercel CLI version; update it through review. Do not enable automatic Git production deployments alongside this manual approval flow. No project, service or credential is created by merely committing the workflow.

Dispatch preview for reviewed `main`, inspect `/` and `/api/health`, unknown API paths, keyboard behavior, and routing. Production dispatch stages with `--prod --skip-domain`; it does not assign the production domain. After approval and smoke verification, promote that exact staged deployment manually. Document the previous known-good deployment before release and use Vercel rollback if needed. Database migrations require a separate reviewed plan and backup once a database exists.

CodeRabbit is optional. A `.coderabbit.yaml` file configures reviews but does not install the GitHub App. The owner must install/authorize that app for this repository. Do not assume a bot review ran or passed without its actual result. Keep the public repository free of production data regardless of reviewer setup.
