# Tests and delivery

Use Vitest for behavior tests, Testing Library and user-event for UI interactions, and axe-core for semantic checks. Test meaningful states, failures and authorization boundaries when introduced. Prefer user-visible outcomes to implementation details. The shell tests cover the skip link, keyboard theme toggle, semantic accessibility and API status/error contracts. jsdom cannot verify visual contrast or actual screen-reader output.

Run the smallest relevant command while editing, then `pnpm check` before integration. Type checks include the Vercel function entry point using its isolated configuration. API tests include a native Node import of the compiled package from the web workspace and actual health/error responses. The Vite build alone does not bundle Vercel serverless functions; remote preview verification is required before claiming deployment success. A Vercel READY state is not evidence that function invocation succeeds.

GitHub Actions CI runs on pull requests and pushes to `main`, with read-only repository permission and no service secrets. The Vercel Git integration is disabled for automatic Git deployments. A push to `dev` starts `deploy-dev.yml`: its first job runs the quality checks without deployment secrets, then the deploy job checks out the exact tested dev commit for migrations, uses Vercel's Preview variables scoped to `dev`, and sends that Git reference to Vercel's deployment API. The deployment script itself remains checked out from `main`. `preview.yml` can be run manually from `main` with a `codex/*` or `feature/*` branch; it checks the selected source without deployment secrets, then asks Vercel to build that exact Git reference remotely. Feature previews do not currently have a database and do not run migrations. Production remains a separate manual staged deployment from `main`; after CI, it applies pending migrations using Production variables, stages the deployment, and is never promoted automatically.

Before enabling CD, link the Vercel project with root directory `apps/web`, include sources outside that directory, select Node 24, and configure the install/build/output settings in `apps/web/vercel.json`. Configure GitHub environments `vercel-dev`, `vercel-preview` and `production`, then set `VERCEL_TOKEN` as an environment secret and `VERCEL_ORG_ID` / `VERCEL_PROJECT_ID` as variables. Keep `main` and `dev` allowed in `vercel-dev`, `main` allowed in `vercel-preview` and `production`, and do not require a human reviewer for `vercel-dev` (that would pause the automatic deployment). Keep the preview and production approval rules enabled. Add a `dev` branch from `main` after this pipeline is merged.

On the Vercel Hobby plan, `dev` and feature previews share the standard Preview environment rather than Custom Environments. `vercel-dev` is the GitHub Actions environment for secret scoping; it does not create a separate Vercel runtime environment. The Turso credentials are scoped to the `dev` branch and are used by the dev migration workflow; feature previews do not receive those credentials and have no database until an isolated preview database is provisioned. Do not point feature previews at the shared dev or production database. Vercel supports Preview variables scoped to a Git branch; Custom Environments require Pro or Enterprise. See [Vercel environments](https://vercel.com/docs/deployments/environments), [branch-specific environment variables](https://vercel.com/docs/environment-variables/manage-across-environments), and [running commands with Vercel environment variables](https://vercel.com/docs/cli/env#running-commands-with-environment-variables).

Run **Create feature preview** from the `main` workflow ref, enter a source branch under `codex/` or `feature/`, and use the resulting URL from the workflow environment. The `dev` deployment uses Vercel's standard Preview target and its stable branch alias; the workflow selects the alias for `dev` and falls back to the unique deployment URL if Vercel does not return it. Inspect `/`, `/api/health`, unknown API paths, keyboard behavior, and routing on both environments. The production workflow stages with `--prod --skip-domain`; it does not assign the production domain. After owner approval and smoke verification, promote that exact staged deployment manually. Document the previous known-good deployment before release and use Vercel rollback if needed. Drizzle records applied migration files and skips them on later runs. Serialize deploys per database; production migrations must remain backward-compatible with the currently deployed app, and destructive changes need a separate recovery plan because code rollback does not reverse schema changes.

CodeRabbit is optional. A `.coderabbit.yaml` file configures reviews but does not install the GitHub App. The owner must install/authorize that app for this repository. Do not assume a bot review ran or passed without its actual result. Keep the public repository free of production data regardless of reviewer setup.
