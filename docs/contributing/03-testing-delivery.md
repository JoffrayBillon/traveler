# Tests and delivery

Use Vitest for behavior tests, Testing Library and user-event for UI interactions, and axe-core for semantic checks. Test meaningful states, failures and authorization boundaries when introduced. Prefer user-visible outcomes to implementation details. The shell tests cover the skip link, keyboard theme toggle, semantic accessibility and API status/error contracts. jsdom cannot verify visual contrast or actual screen-reader output.

Run the smallest relevant command while editing, then `pnpm check` before integration. Type checks include the Vercel function entry point using its isolated configuration. API tests include a native Node import of the compiled package from the web workspace and actual health/error responses. The Vite build alone does not bundle Vercel serverless functions; remote preview verification is required before claiming deployment success. A Vercel READY state is not evidence that function invocation succeeds.

GitHub Actions CI runs on pull requests and pushes to `main` and `dev`, with read-only repository permission and no service secrets. Vercel's automatic Git deployments are disabled in `apps/web/vercel.json`. After a successful `CI` push to `dev`, `deploy-dev.yml` runs three sequential jobs: verify the CI result, migrate the Vercel Preview database scoped to `dev`, then deploy the tested commit. After successful `CI` on `main`, `deploy.yml` accepts only successful pushes to this repository's `main` branch, then runs as one protected Production job with explicit migration and deploy steps. It rechecks that the tested SHA is still the tip of `main` after migration, so an old rerun cannot replace a newer release. Keeping these steps in one job means any required Production approval occurs before the migration, rather than asking for a second approval after the database has changed. The `development` and `production` environments record the deployed URLs. Migration steps use `vercel env run`, so credentials are fetched just in time and are not written to files or copied into GitHub secrets. `workflow_run` workflows must exist on the default branch, so updates to the dev deployment workflow become active after they reach `main`; until then, the version already on `main` handles dev deployments. `preview.yml` can be run manually from `main` with a `codex/*` or `feature/*` branch; it checks the selected source without deployment secrets, then asks Vercel to build that exact Git reference remotely. Feature previews do not run migrations.

The Vercel project uses root directory `apps/web`, includes sources outside that directory, runs Node 24 and reads its build settings from `apps/web/vercel.json`. GitHub deployment jobs use the `development`, `preview` and `production` environments. Each job that uses Vercel needs `VERCEL_TOKEN` as an environment secret and `VERCEL_ORG_ID` / `VERCEL_PROJECT_ID` as variables. Restrict `development` and `preview` to the `main` workflow ref, and `production` to `main`; required reviewers on `preview` and `production` gate their deployments before they run. The trusted `dev` workflow checks out the SHA tested by CI and accesses deployment credentials for migration and deployment, so protect `dev` to accept only reviewed PR merges. Keep `development` free of required reviewers so the `dev` push can deploy automatically.

On the Vercel Hobby plan, `dev` and feature previews share the standard Preview environment rather than Custom Environments. `development` is the GitHub Actions environment for deployment-token scoping; it does not create a separate Vercel runtime environment. The Turso credentials are scoped to the `dev` branch and used only by that branch's migration step and deployment; feature-preview workflows do not migrate or receive database credentials. Do not point feature previews at the shared dev or production database. Vercel supports Preview variables scoped to a Git branch; Custom Environments require Pro or Enterprise. See [Vercel environments](https://vercel.com/docs/deployments/environments), [branch-specific environment variables](https://vercel.com/docs/environment-variables/manage-across-environments), and [system environment variables](https://vercel.com/docs/environment-variables/system-environment-variables).

Run **Create feature preview** from the `main` workflow ref, enter a source branch under `codex/` or `feature/`, and use the resulting URL from the workflow environment. The `dev` deployment uses Vercel's standard Preview target and its stable branch alias; the workflow selects the alias for `dev` and falls back to the unique deployment URL if Vercel does not return it. The production deployment uses the configured production domain when Vercel returns it, otherwise the unique deployment URL. GitHub's repository **Deployments** page lists the `development`, `preview` and `production` environments and their latest URLs. Inspect `/`, `/api/health`, unknown API paths, keyboard behavior, and routing on both environments. Drizzle records applied migration files and skips them on later runs. Serialize deploys per database; production migrations must remain backward-compatible with the currently deployed app, and destructive changes need a separate recovery plan because code rollback does not reverse schema changes.

CodeRabbit is optional. A `.coderabbit.yaml` file configures reviews but does not install the GitHub App. The owner must install/authorize that app for this repository. Do not assume a bot review ran or passed without its actual result. Keep the public repository free of production data regardless of reviewer setup.
